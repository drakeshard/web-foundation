# Web Foundation v0.1 Usage Guide

## Status

Release-candidate integration guide for the S08-01 finalized public surface.

This guide documents implemented v0.1 behavior only. It does not define a renderer framework, game
domain model, shared UI layer, schema package, or distribution mechanism.

S08-05 / #89 will decide whether the first consumer uses a workspace, GitHub/tag dependency, private
registry, or another approved mechanism. Until then the packages remain private and this guide uses
package-name imports as they resolve inside the repository workspace/consumer validation fixture.

## Public entry points

`@drakeshard/foundation`:

- `@drakeshard/foundation/time`;
- `@drakeshard/foundation/random`;
- `@drakeshard/foundation/input`;
- `@drakeshard/foundation/input/browser`;
- `@drakeshard/foundation/storage`;
- `@drakeshard/foundation/storage/browser`.

`@drakeshard/testing`:

- `@drakeshard/testing/clock`.

There is intentionally no package-root import such as `@drakeshard/foundation`.

## Integration shape

A browser game owns orchestration around Foundation:

```text
browser / renderer frame
        |
        +--> browser input adapters --> physical records
        |                              |
        |                              v
        |                     action/context mapping
        |                              |
        |                              v
        |                        tick handoff
        |
        +--> FixedStepDriver.advance(frameDeltaMs)
                         |
                         +--> 0..N deterministic game ticks
                         |       |
                         |       +--> consume tick input
                         |       +--> update game/domain state
                         |       +--> consume deterministic RNG
                         |
                         +--> interpolation alpha --> renderer presentation

explicit app boundary
        |
        +--> game-owned save payload
                |
                v
        EnvelopeSaveService --> SaveStorage --> IndexedDB
```

Foundation does not own `requestAnimationFrame`, renderer lifecycle, game commands, domain state,
screen/world conversion, UI state, or save-payload schemas.

## Fixed-step simulation

Import:

```ts
import { FixedStepDriver } from "@drakeshard/foundation/time";
```

The application/renderer owns the frame callback and supplies elapsed milliseconds:

```ts
const fixedStep = new FixedStepDriver({
  stepMs: 1000 / 60,
  maxFrameDeltaMs: 250,
  maxStepsPerFrame: 5,
});

function onRenderFrame(frameDeltaMs: number): void {
  const frame = fixedStep.advance(frameDeltaMs);

  for (let index = 0; index < frame.steps; index += 1) {
    runOneGameTick();
  }

  renderFromAuthoritativeState(frame.alpha);

  if (frame.overrun) {
    // Optional app-owned diagnostics.
    recordDroppedSimulationSteps(frame.droppedSteps);
  }
}
```

Rules:

- one executed tick represents exactly the configured `stepMs`;
- domain/simulation code does not read wall-clock time;
- `alpha` is presentation-only and must not mutate authoritative state;
- Foundation reports overruns but does not log or render diagnostics.

For a pause, hidden tab, or intentional suspension, reset the application's elapsed-time baseline and
call `fixedStep.reset()` before feeding new elapsed time. Do not pass the whole background duration
back into the driver.

### Phaser example

Phaser may supply its Scene frame delta to app-owned fixed-step orchestration:

```ts
class GameScene extends Phaser.Scene {
  update(_time: number, deltaMs: number): void {
    const frame = fixedStep.advance(deltaMs);

    for (let step = 0; step < frame.steps; step += 1) {
      runOneGameTick();
    }

    syncPhaserPresentation(domainState, frame.alpha);
  }
}
```

`Phaser.Scene`, GameObjects, canvas scaling, and world-coordinate conversion stay application-local.
The example is an integration pattern, not a promised `@drakeshard/phaser` adapter API.

### PlayCanvas example

PlayCanvas may likewise remain the render-loop owner while the application decides when/how to
advance deterministic simulation:

```ts
app.on("update", (deltaSeconds: number) => {
  const frame = fixedStep.advance(deltaSeconds * 1000);

  for (let step = 0; step < frame.steps; step += 1) {
    runOneGameTick();
  }

  syncPlayCanvasPresentation(domainState, frame.alpha);
});
```

The current repository probe deliberately demonstrates some PlayCanvas domain changes through
explicit app-level commands rather than claiming this exact frame-loop shape as a shared adapter.
`pc.Application`, `pc.Entity`, camera/ray/elevation logic, and renderer presentation rebuilding
remain application-local.

## Deterministic RNG

Import:

```ts
import {
  DeterministicRng,
  RNG_ALGORITHM_ID,
  type DeterministicRngState,
} from "@drakeshard/foundation/random";
```

Create from an explicit unsigned 32-bit seed:

```ts
const rng = new DeterministicRng(12345);

const raw = rng.nextUint32();
const unit = rng.nextFloat01();
const savedState = rng.snapshot();
```

Resume exactly from a stored state:

```ts
const restored = DeterministicRng.fromState(savedState);
```

Compatibility rules:

- v0.1 algorithm id is `xoshiro128starstar-v1`;
- identical initial state + identical ordered RNG method calls yields the same sequence;
- changing draw order changes later results;
- `snapshot()` does not consume a draw;
- games that need save/replay RNG continuity store the RNG snapshot in their game-owned payload;
- Foundation storage does not implicitly persist RNG state;
- this RNG is not cryptographically secure.

Consumers should persist or otherwise know `RNG_ALGORITHM_ID` whenever compatibility depends on a
stored RNG state.

## Browser input to tick consumption

Imports:

```ts
import {
  ActionBindingResolver,
  InputContextRouter,
  MonotonicInputSequence,
  TickInputHandoff,
  type PhysicalInputSink,
} from "@drakeshard/foundation/input";
import {
  BrowserInputLifecycle,
  KeyboardBrowserAdapter,
  PointerBrowserAdapter,
} from "@drakeshard/foundation/input/browser";
```

One shared monotonic sequence source should order all physical adapters feeding the same pipeline:

```ts
const sequence = new MonotonicInputSequence();

const actions = new ActionBindingResolver([
  {
    action: "gameplay.primary",
    binding: { kind: "key", code: "Space" },
  },
  {
    action: "gameplay.primary",
    binding: { kind: "pointer-button", button: 0 },
  },
]);

const contexts = new InputContextRouter([
  {
    id: "gameplay",
    priority: 0,
    actions: [{ action: "gameplay.primary" }],
  },
  {
    id: "modal",
    priority: 100,
    actions: [{ action: "gameplay.primary", consume: true }],
  },
]);

contexts.activate("gameplay");

const handoff = new TickInputHandoff({ actions, contexts });
const sink: PhysicalInputSink = (event) => handoff.ingest(event);

const lifecycle = new BrowserInputLifecycle({
  focusTarget: window,
  visibilityTarget: document,
  sequence,
  sink,
});

const keyboard = new KeyboardBrowserAdapter({
  keyboardTarget: window,
  lifecycle,
  sequence,
  sink,
});

const pointer = new PointerBrowserAdapter({
  pointerTarget: canvas,
  wheelTarget: canvas,
  lifecycle,
  sequence,
  sink,
});

lifecycle.attach();
keyboard.attach();
pointer.attach();
```

At the deterministic game-tick boundary:

```ts
function runOneGameTick(): void {
  const input = handoff.consumeTick();

  for (const action of input.actions) {
    if (
      action.context === "gameplay" &&
      action.action === "gameplay.primary" &&
      action.pressed
    ) {
      domainApply({ kind: "primary-action" });
    }
  }

  for (const command of input.commands) {
    applyQueuedGameCommand(command);
  }

  updateDomain();
}
```

Important boundaries:

- DOM event objects never enter deterministic game/domain contracts;
- `KeyboardEvent.code` and browser pointer data are physical identity, not game semantics;
- action ids and context ids are application-owned opaque strings;
- input ordering uses `InputSequence`, not browser timestamps;
- blur/hidden/detach resets invalidate held input rather than inventing gameplay release commands;
- raw pointer positions are viewport CSS pixels;
- screen-to-world conversion remains renderer/application-local;
- application code translates Foundation actions/commands into actual game-domain commands.

A modal UI can activate a higher-priority context without making UI state authoritative:

```ts
function setModalOpen(open: boolean): void {
  if (open) contexts.activate("modal");
  else contexts.deactivate("modal");
}
```

## Settings storage

For small synchronous preferences:

```ts
import { LocalStorageSettingsStorage } from "@drakeshard/foundation/storage/browser";

const settings = new LocalStorageSettingsStorage({
  storage: window.localStorage,
  namespace: "my-game",
});

const write = settings.write("audio.volume", 0.8);
if (!write.ok) {
  showSettingsError(write.error.kind);
}

const read = settings.read("audio.volume");
if (read.ok && typeof read.value === "number") {
  applyVolume(read.value);
}
```

Settings values are JSON-compatible. Game-specific validation remains application-owned.

## Save storage, envelopes, versions, and migrations

Imports:

```ts
import {
  EnvelopeSaveService,
  SaveMigrationRegistry,
  type JsonValue,
} from "@drakeshard/foundation/storage";
import { IndexedDbSaveStorage } from "@drakeshard/foundation/storage/browser";
```

Build one app-owned save composition:

```ts
const rawSaves = new IndexedDbSaveStorage({
  databaseName: "my-game-saves",
});

const migrations = new SaveMigrationRegistry([
  {
    sourceVersion: 1,
    targetVersion: 2,
    migrate(payload: JsonValue) {
      // Validate/narrow enough to perform this game-owned migration safely.
      return { ok: true, value: payload };
    },
  },
]);

const saves = new EnvelopeSaveService<JsonValue>({
  storage: rawSaves,
  gameId: "my-game",
  saveFormatVersion: 2,
  gameVersion: "0.1.0",
  contentVersion: "content-1",
  migrations,
  now: () => new Date().toISOString(),
});
```

Save only renderer-neutral, JSON-compatible application/domain data:

```ts
const payload = extractGameSavePayload(authoritativeState);
const saved = await saves.save("slot-1", payload);

if (!saved.ok) {
  showSaveError(saved.error.kind);
}
```

Load at an explicit application boundary:

```ts
const loaded = await saves.load("slot-1");

if (!loaded.ok) {
  showLoadError(loaded.error.kind);
} else if (loaded.value !== null) {
  const decoded = decodeGameSavePayload(loaded.value);

  if (decoded.ok) {
    restoreAuthoritativeState(decoded.value);
    rebuildRendererPresentationFromDomain();
  } else {
    showGamePayloadValidationError(decoded.errors);
  }
}
```

Version ownership:

- `saveFormatVersion` controls Foundation migration sequencing;
- `gameVersion` records the application/game release identifier;
- `contentVersion` records application-owned content/data compatibility metadata;
- Foundation package version is release metadata and is not a save-format key.

Migration rules:

- migrations advance exactly one save-format version at a time;
- loading may migrate in memory through a complete sequential chain;
- load-time migration is non-committing;
- a migrated source record is not silently overwritten;
- committing a current save is a later explicit `save` operation.

Failure handling:

- expected persistence/platform failures are returned as `PersistenceResult`;
- consumers branch on stable `kind` / `operation`;
- browser exception types and raw IndexedDB objects are not public compatibility contracts.

## Game-owned payload validation

Foundation validates its generic envelope and JSON-compatible payload boundary. It does not know your
game schema.

Validate untrusted/loaded payloads before they become authoritative domain state:

```ts
const loaded = await saves.load("slot-1");

if (loaded.ok && loaded.value !== null) {
  const decoded = decodeGameSavePayload(loaded.value);

  if (!decoded.ok) {
    // Application-owned readable/schema errors.
    reportInvalidSave(decoded.errors);
    return;
  }

  restoreAuthoritativeState(decoded.value);
}
```

A game may use a local custom validator, Zod, Valibot, or another application-selected solution.
Validator packages and error types do not become Foundation dependencies merely because they are
useful to a game.

## Diagnostics ownership

Foundation exposes operational evidence through normal return values such as:

- `FixedStepAdvanceResult.clampedMs`;
- `FixedStepAdvanceResult.droppedSteps`;
- `FixedStepAdvanceResult.overrun`;
- structured `PersistenceResult` failures;
- input snapshots/transitions/commands.

The application owns logging, telemetry, counters, debug panels, retained event buffers, and UI.
v0.1 does not provide a generic diagnostics registry or debug UI package.

## UI ownership

Application UI remains application-owned.

A UI layer may:

- read projections copied/derived from authoritative domain state;
- hold transient presentation state;
- emit intentions to application orchestration;
- activate/deactivate input contexts.

It must not become authoritative gameplay state merely because a renderer or UI framework owns its
objects/signals.

The repository probes use Preact as application UI evidence. That does not make Preact a dependency
or public type of either shared package.

## Renderer ownership

Renderer objects are disposable presentation.

Do not place Phaser GameObjects, PlayCanvas Entities, cameras, rays, transforms, renderer input
events, or renderer-specific coordinates into authoritative game/domain contracts or save payloads.

Recommended restore pattern:

1. load and application-validate renderer-neutral domain data;
2. restore authoritative domain state;
3. republish any UI projection;
4. discard/recreate renderer presentation from the restored state.

## Testing support

`@drakeshard/testing/clock` exposes only `ManualClock`:

```ts
import { ManualClock } from "@drakeshard/testing/clock";

const clock = new ManualClock(1000);
clock.advanceBy(16);
```

Use it for deterministic tests that need caller-owned monotonic time. It does not make
`FixedStepDriver` clock-driven; the test/application still supplies elapsed time explicitly.

## Current browser evidence

The release candidate is continuously exercised by:

- a full Chromium Playwright suite;
- focused Firefox compatibility pressure tests;
- focused WebKit compatibility pressure tests.

Current limits are documented in `docs/testing/browser-compatibility.md`. In particular, Playwright
WebKit on hosted Linux is not a claim of native Safari/device certification, and the full
PlayCanvas/WebGL-heavy suite remains Chromium-only.

## What v0.1 deliberately does not provide

Do not infer support for systems outside the finalized public surface, including:

- renderer adapters or a universal renderer loop;
- scene graphs or presentation entity frameworks;
- shared UI/components/signals;
- generic schema/decoder/error frameworks;
- generic diagnostics/telemetry/counter registries;
- ECS;
- networking/rollback/protocols;
- audio/localization;
- combat, RPG, Tactical, jobs/classes/skills/stats, AI, quests, progression, inventory, or other
  game-domain systems.

Those belong to applications or separately governed libraries unless later evidence admits a
narrower shared contract.
